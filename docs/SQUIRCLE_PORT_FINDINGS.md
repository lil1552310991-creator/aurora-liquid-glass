## 二、参数语义（照抄源码，不要凭直觉）

```text
tW = clamp((width  * 0.5 - r) / r, 0, 1)
tH = clamp((height * 0.5 - r) / r, 0, 1)
p  = cornerBuilder.getCornerBezierPoints(tW, tH)
r  = radius.toDouble()          // 注意：不做 maxRadius 夹取！
```

**重要**：`continuousCurvatureRoundedRectanglePath(size, radius)` 这个重载
**没有**把 radius 夹到 `minDimension * 0.5`。更正一处早期误记：`RoundedRectangleOutline.kt:18`
的 `maxRadius` **只用于第 24 行 `width == height && radius >= maxRadius` 这一个分支判断**，
并不会夹取后再传进来 —— 该文件里其实**没有任何夹取**（夹取若有，发生在更上层）。
调用方需要自己限制 radius，且实际约束比 `min(w,h)/2` 更紧，
见 [`SQUIRCLE_PATH_FIX.md`](SQUIRCLE_PATH_FIX.md) 第四节第 2 条。

`tW` 与内部变量的对应关系（源码 `buildEven` / `buildUneven`）：

```text
kV = extendedFraction * tW      // 作用于 kappa6 / x0p（竖向那一族）
kH = extendedFraction * tH      // 作用于 kappa3 / x0  （横向那一族）
```

即 **tW 对应 k 的「V」那一族**，与命名直觉相反。

## 三、四角基准点与变换（逐行核对 `RoundedRectangleOutline.kt:111-185`）

Compose 坐标：**y 向下**，原点左上。

| 角 | 基准 (x, y) | x 用 | y 用 | 索引 |
| --- | --- | --- | --- | --- |
| 右上 | `(w - r, 0)` | `+p[i]` | `+p[i]` | 正序 0→18 |
| 右下 | `(w - r, h)` | `+p[i]` | `-p[i]` | **倒序 18→0** |
| 左下 | `(r, h)` | `-p[i]` | `-p[i]` | 正序 0→18 |
| 左上 | `(r, 0)` | `-p[i]` | `+p[i]` | 倒序 18→0 |

注意：**右下角是倒序、左下角是正序**（两者不对称！）。
判据是各角第一句 `lineTo` 用的是哪个下标：
右下从 `p[18]` 起（源码 132 行）、左下从 `p[0]` 起（源码 151 行）、左上从 `p[18]` 起（源码 170 行）。
早期版本在此处判断错了两次，最终由 [`SQUIRCLE_PATH_FIX.md`](SQUIRCLE_PATH_FIX.md) 定位并修正。

## 四、三次贝塞尔的分段方式（关键，曾判断错）

三段 cubic 的点组是：

```text
段1: (P0, P1, P2, P3)
段2: (P3, P4, P5, P6)
段3: (P6, P7, P8, P9)
```

**不是** `(P0,P2,P4,P6)`。判据：只有这个分组能让三段首尾相接
（上一段终点 = 下一段起点），而源码的第一个 cubicTo 恰好以 `p[6], p[7]` 为终点。

## 五、每条边还需补一段直线

角在每条边上的延伸量是 **`(1 + extendedFraction) * r = 5r/3`**，不是 `r`。
因此相邻两个角之间还隔着一段直线，必须显式补上（源码中的 `lineTo`）。

在 620x900、r=46 上实测的四角端点（**按路径行进方向**，起→止）：

```text
右上 起(543.333,   0.000)  止(620.000,  76.667)     上边 -> 右边
右下 起(620.000, 823.333)  止(543.333, 900.000)     右边 -> 下边
左下 起( 76.667, 900.000)  止(  0.000, 823.333)     下边 -> 左边
左上 起(  0.000,  76.667)  止( 76.667,   0.000)     左边 -> 上边
```

（早期版本这里记录的是 `右下 起(543.333,900)` / `左下 起(0,823.333)`，
那是索引方向弄反后的**反向**遍历结果 —— 端点坐标集合相同，但方向相反，
所以包围盒与闭合距离照样正确。见 [`SQUIRCLE_PATH_FIX.md`](SQUIRCLE_PATH_FIX.md)。）

加入四条直线段后：

```text
首尾距离 = 0.000        => 闭合
包围盒 x[0.00, 620.00] y[0.00, 900.00]  => 零越界
```

## 六、已解决：填充形状错误（梯形）

**结论：右下角与左下角的贝塞尔索引方向被互换。** 详见
[`SQUIRCLE_PATH_FIX.md`](SQUIRCLE_PATH_FIX.md)。此处保留问题描述与教训。

现象：路径已闭合并零越界，但填充渲染出的形状是「上宽下窄的梯形」，
而不是圆角矩形。标准圆弧版本（对照）渲染正常。

为什么端点类检查全部失效：

- **不是算法算错**（`docs/CORNER_PORT_AUDIT.md` 已逐位证明 1138 个量 0 差异）
- **不是索引自洽性问题**（审计确认 P3/P6 共享端点、分段方式正确）
- **不是闭合问题**（首尾距离已为 0）
- **不是越界问题**（包围盒精确）
- **不是缩放/填充代码问题**（同一份填充代码画标准圆弧是正确的）

根因的性质：**把一段 cubic 链的索引方向反过来，走过的是同一组点，只是方向相反。**
所以该角的形状、端点坐标集合、包围盒、闭合距离**全都不变** ——
「闭合 + 零越界」这两个指标在原理上就不可能发现它。
被破坏的只有**角与角之间的衔接方向**。

教训（可推广）：

1. 端点类检查对「方向反转」完全不敏感。必须补一条**连续性**断言：
   上一段的止点与下一段的起点之间，过渡采样点必须全程落在面板边界上。
2. 另一条廉价而有效的判据是**总转角**：正确的凸形闭合曲线恒为 +360°；
   方向反转会把它变成 −360°。
3. 最彻底的做法是写一份**源码逐行转写**的参考实现，与生成结果逐点比对
   （修复后 `maxDev = 0.000000000 px`）。
4. 旧版自检其实已经把证据打印在屏幕上（`接缝: 右上->右下 间距 826.895`），
   只是没有把它变成断言。**打印出来的数字要变成断言才有意义。**

## 八、给 shader 落地的建议（不依赖第六节的结论）

### 8.0 一个必须知道的事实：Kyant 的 shader 里没有连续曲率 SDF

`docs/KYANT_GLASS_TECH.md` 核实了这一点（附逐字代码块校验）：

- Kyant 的 `backdrop` 库在 shader 里用的是**标准圆角矩形 SDF**
  （`backdrop/src/commonMain/kotlin/com/kyant/backdrop/internal/Shaders.kt:22-48`）：
  ```glsl
  q = abs(p) - (halfSize - r);
  sd = length(max(q, 0.0)) - r + min(max(q.x, q.y), 0.0)
  ```
  四角是**正圆**，不是连续曲率。
- 那 10 个 Bézier 控制点**只用于 `cubicTo` 画轮廓路径**。
- **轮廓与折射用的 SDF 在源码层面是脱节的两套东西。**
  所以「Bézier 控制点 → 距离场」这段代码**在仓库里根本不存在**，
  不可能从源码推出来，必须自己补。

真正把 SDF 当距离场用的只有一处：预烘焙贴图 `clock_sdf.webp`。
其 shader 全文在 `app/src/commonMain/kotlin/com/kyant/backdrop/catalog/utils/SdfShader.kt:35-75`：

```glsl
half4 v = sdfTex.eval(p);
float sd = v.r * 2.0 - 1.0;
v.a = smoothstep(0.5, 1.0, v.a);
if (v.a < 1.0) { sd = 0.0; }
float2 normal = normalize(v.gb * 2.0 - 1.0);
float intensity = circleMap(1.0 - min(1.0, -sd * 1.5));
float2 refractedCoord = coord - intensity * refractionHeight * normal;
```

该贴图已被逐像素解码（VP8L 无损），反推出的烘焙规格：

| 通道 | 内容 | 公式 |
| --- | --- | --- |
| R | 有符号距离 | `clamp(round(128 − 2.36·d_in), 0, 128)` |
| G | 外法线 x | `127.5 + 127.5·n.x` |
| B | 外法线 y | `127.5 + 127.5·n.y` |
| A | 向外覆盖度 | `clamp(round(255 − 18.4·d_out), 0, 255)` |

注意 GB 存的是**边界最近点的外法线**（不是像素梯度，所以内部呈块状）。

**这条事实直接改变了落地方案**：既然 Kyant 自己都用标准圆角矩形 SDF，
那么 `boxMetric` 并不是「妥协」，而是**与参考实现同构**。
连续曲率圆角只是轮廓层的差异，属精度升级，不应阻塞主链路。

### 8.1 超椭圆逼近：已验证不可行

`build/recon/squircle_sdf_calib.cpp` 试过用超椭圆 `|u|^n + |v|^n = 1` 逼近，
结果是**明确失败**：

```text
n = 2.00  ->  max|pred - actual| = 0.953262   (单位: r)
n = 5.00  ->  max|pred - actual| = 0.968553
最佳 n = 2.00, 最大偏差 = 0.953
```

根因：精确曲线的支撑域是 `5r/3 × 5r/3`，而超椭圆的支撑域固定为 `1 × 1`，
**两者不是同一个域，直接比较 f 值无意义**。

结论：**放弃超椭圆逼近**。可选方案只剩：

1. **把 SDF 预烘焙成纹理传入 shader** —— 这正是 Kyant 在 `SdfShader.kt` 里的做法，
   且审计已给出完整的通道规格，可直接照做。
2. **精确 Bézier 几何通道** —— 形状最准，但要额外的几何通道。
3. **直接用标准圆角矩形 SDF** —— 与参考实现同构，零风险，推荐作为第一步。

### 8.2 两条可直接搬运的公式

来自 GlassExplorer 的参数测绘（参考实现见 AndroidLiquidGlass `Shaders.kt`）：

1. **伪造玻璃厚度**（一行改动，让玻璃从「一张纸」变成「有体积的透镜」）：
   ```glsl
   grad = normalize(gradSdRoundedRect(...) + depthEffect * normalize(centeredCoord));
   ```
2. **边缘高光**：`pow(abs(dot(grad, lightDir)), falloff)`，
   且梯度半径须取 `min(r * 1.5, min(halfW, halfH))` 才能让亮边沿直边延伸。
