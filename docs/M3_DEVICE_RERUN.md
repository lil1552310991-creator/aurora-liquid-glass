## 四、`aurora_demo` 的状态（未完成的部分）

演示程序（`root-host/elf/`）在真机上**跑到第 2 步就崩**：

```
[1/5] client 已构造          ← 通过
[2/5] 图层已创建 = 0x7ffd1f54b0   ← 通过
Segmentation fault                ← 崩在 getSurface
```

### 已修掉的两个真实 bug

**1. `Client` 缓冲区过小（已修）**

```cpp
// 错：只有 256 字节
alignas(16) char storage[256]{};
// 对：与探针一致
alignas(std::max_align_t) char d[1024];
```

`SurfaceComposerClient` 的真实对象大于 256 字节，`clientCtor` 写越界
踩坏相邻内存，表现为**进程卡死**（不是崩溃，更难查）。

**2. `String8W`/`MetaW` 缓冲区偏移错误（已修）**

```cpp
// 错：缓冲区被推到偏移 8
struct String8W { void* pointer; char padding[64]; };
// 对：缓冲区必须在偏移 0
struct String8W { char d[64]; void* p() { return d; } };
```

libgui 的构造函数把对象写在传入指针处，所以任何「先放一个成员再放缓冲区」
的写法都会让对象落到错误偏移上。

**3. 符号解析的间接层（已修）**

原本把 `dlsym` 结果一次性存进结构体成员再调用。改成探针那样
**在调用点现解析**后，图层创建就通了。跨 libgui ABI 调用时这层间接不可靠。

### 仍未解决：`getSurface` 返回时崩溃

```
libgui 符号全部解析成功（地址都在 libgui 映射内，已打印核对）
createSurface 成功，返回 0x7fd2aa5ca0
调用 getSurface 后立即 SIGSEGV
```

**注意返回值的差异**：探针拿到的是 `0xb400007efb43c300`（堆地址，
Android ScopedAllocator 的 `0xb4...` 特征），我的演示拿到的是 `0x7ffd...`
（栈地址）。类型形态已改成与探针逐字一致的模板版，仍然崩。

**下一步建议**：不要再"重新实现"这段，直接**把探针的
`Client` / `StrongPointer` / `R()` 三段整块复制**到演示里 —— 它们在真机上
已被证明可用。逐个字段对齐是低效且已两次失败的做法。

## 五、一个重要的方法论教训

这次调试暴露的问题：我多次从子代理的**报告文字**转述代码，而不是
**拷贝实际验证过的源码**，导致：

- 四角表的 `rev` 标志抄反（M3.5 那 22% 面积偏差的直接原因）
- `String8W` 的缓冲区偏移抄错
- `StrongPointer` 写成非模板形态

**规则**：凡是「已被真机或数值验证过」的代码，移植时必须**整块复制**，
不重新实现、不"简化"、不按描述转写。描述用于理解，代码用于复用。
