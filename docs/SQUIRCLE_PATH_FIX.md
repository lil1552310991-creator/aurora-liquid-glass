## 一、错误根源

`ccrr_fill.cpp` 把源码里**右下角**与**左下角**的贝塞尔控制点索引方向弄反了 —— 两者恰好互换。

修复前的两行（旧文件行号）：

```cpp
// 第 169 行：右下角 —— 源码要求【倒序】，旧代码传了 false（正序）
n = emitArc(p, r, W-r, H,   +1, -1, false, S, out, n, cap);

// 第 173 行：左下角 —— 源码要求【正序】，旧代码传了 true（倒序）
n = emitArc(p, r, r,   H,   -1, -1, true,  S, out, n, cap);
```

对应的修复（新文件 `buildPath` 里的四角表）：

```cpp
const CornerDef cs[4] = {
    { W - r, 0.0, +1, +1, false, "右上", 111 },  // 正序
    { W - r, H,   +1, -1, true,  "右下", 130 },  // 倒序  ← 旧代码为 false
    { r,     H,   -1, -1, false, "左下", 149 },  // 正序  ← 旧代码为 true
    { r,     0.0, -1, +1, true,  "左上", 168 },  // 倒序
};
```

### 逐行依据

| 角 | 源码行 | 该角的第一句 | 索引方向 |
| --- | --- | --- | --- |
| 右上 | 113-128 | `moveTo(x+p[0], y+p[1])` 后 `cubicTo(x+p[2],y+p[3], x+p[4],y+p[5], x+p[6],y+p[7])` | 递增 0→18 |
| **右下** | **132-147** | `lineTo(x+p[18], y-p[19])` 后 `cubicTo(x+p[16],y-p[17], x+p[14],y-p[15], x+p[12],y-p[13])` … 直到 `x+p[0], y-p[1]` | **递减 18→0** |
| **左下** | **149-166** | `lineTo(x-p[0], y-p[1])` 后 `cubicTo(x-p[2],y-p[3], x-p[4],y-p[5], x-p[6],y-p[7])` … 直到 `x-p[18], y-p[19]` | **递增 0→18** |

### 关于「哪个重载被调用」与「P1/P3/P5 是否被跳过」

- 实际被 `roundedRectangleOutline()`（第 41 行）调用的是**单半径**重载（第 92-189 行）；多半径重载（第 191-309 行）只在四角半径不同时使用。两者的四角映射**逐行一致**（132 与 240、151 与 265 完全相同），所以这个选择不影响结论。
- 此前的另一个怀疑可以排除：`cubicTo` 的第一个参数对**就是 cp1**，不是起点。`moveTo` 之后的第一个 `cubicTo(p[2],p[3], p[4],p[5], p[6],p[7])` 的三个参数依次是 (cp1, cp2, 终点)，起点由 `moveTo` 给出。因此 **P1、P3、P5 全都被用到**，三段是 `(P0,P1,P2,P3)`、`(P3,P4,P5,P6)`、`(P6,P7,P8,P9)` —— 与 `SQUIRCLE_PORT_FINDINGS.md` 第四节的结论一致，不存在被跳过的控制点。旧版在这一点上没有错。

## 二、为什么「闭合 + 零越界」发现不了它

核心性质：**把一段 cubic 链的索引方向反过来，走过的是同一组点，只是行进方向相反。**

由此：

- 该角曲线的形状不变，端点的**坐标集合**也不变 → 包围盒仍然精确、零越界；
- 每个角自身内部仍然首尾相接 → 角内的相邻采样点没有跳变，也不自交；
- 「首尾距离」只比较路径的第一个点和最后一个点（分别位于右上角和左上角，没有被这个 bug 波及）→ 依然精确为 0。

被破坏的只有**角与角之间的衔接方向**。这一个错误造成 826.9 px 与 620.0 px 两处跳跃，扫描线填充按奇偶规则把这两处的区域判成外部：

- 右上角止点 `(620, 76.667)` 之后没有沿右边继续向下，而是斜穿到右下角起点 `(543.333, 900)`；
- 右下角本身被反向遍历，与那条斜线围出一个「回退环」；
- 左下角同理，于是面板被渲染成**上宽下窄的梯形**，底部还残留两片脱离的角。

实测（`--legacy` 模式）：

```text
有符号面积 = 447344.4 px^2     （正确值 556045.6）
总转角     = -360.0057 deg     （正确值 +359.99）
真自交数   = 2                 （正确值 0）
```

**旧版自检其实已经把证据打在屏幕上了**，只是没有把它变成断言：

```text
接缝:
  右上->右下 间距 826.895
  右下->左下 间距 620.000
```

## 四、顺带确认的两条定量结论

1. **45° 处半径 = 1.0000 r**，与此前用另一个程序测得的结果一致。最大内收 0.9837 r 出现在极角 83.02°（极点是参考点 `(W-r, r)`）。也就是说这条曲线在 45° 对角线上与半径 r 的标准圆弧**完全重合**，只在两侧略微内收（≤1.63%）。
   - 与「同切点长度的圆弧」相比（该圆弧半径 5r/3），单角切掉的面积从 0.5961 r² 降到 0.2309 r²，即**饱满 158%**。
   - 与「半径 r 的标准圆弧」相比，单角切掉面积 0.2309 r² vs 0.2146 r²，总面积只差 −136.8 px²（−0.02%）。

2. **该构造有定义域限制**：角在每条边上的延伸量是 `(1+k)·r`，两条同向边的延伸量之和不能超过面板尺寸。对 620x900 且 `tW=tH=1` 的情形，上限为

   ```text
   r ≤ 3·min(W,H)/10 = 186
   ```

   二分法实测边界正是 `186.000000`。超过之后四角互相重叠 —— **源码本身也会画出重叠路径**（参考实现与本文路径仍逐点相同，`dev = 0`），所以这是上游的定义域限制，不是移植错误。因此 `continuousCurvatureRoundedRectanglePath` 不夹取 radius，`ccrr_fill.cpp` 也保持不夹取；**实际渲染时调用方需要自己把 radius 限制到 `min(w,h)/2` 以内，并注意 5r/3 的延伸量带来的更紧的上限**。
