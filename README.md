# Aurora — Android 液态玻璃覆盖层

在 Android 上跑一块**真正的液态玻璃**：折射、色散、边光、内阴影、液滴融合全是实时算出来的，
背景是**实时的屏幕内容**，而且运动物体跨过玻璃边界时**不会撕裂**。

它不是"给 ImGui 换了个皮肤"，而是把 Dear ImGui 搬到了一个它原本没打算运行的地方 ——
**SurfaceFlinger 里的一个裸图层**（不需要 Activity、不需要 WindowManager 窗口），
并把它与 Android 的输入系统、输入法、系统合成器重新接起来。

```
┌─────────────────────────────────────────────┐
│  你的应用 / 游戏 / 桌面                       │
│  ─────────────────────────────────────────   │
│  Aurora 图层：液态玻璃面板 + ImGui 界面        │  ← SF mRoot 的兄弟节点
│  ─────────────────────────────────────────   │     （不在 WMS 窗口树里）
│  触摸：只有玻璃覆盖的地方才被接走               │
└─────────────────────────────────────────────┘
```

---

## 一、它解决的痛点

如果你在 Android 上做过悬浮窗 + ImGui，下面这些坑大概率都踩过。

### 痛点 1：触摸拦截是"全屏"的，会和别的悬浮窗打架

绝大多数悬浮窗方案用一个**全屏输入盾**消费掉所有触摸，再决定哪些转发给自己。
本项目早期形态（Activity 宿主，见第六节）也是这么做的 —— 代码里就是
"一个全屏透明渲染 Surface + 一个全屏透明输入盾"。

**后果**：别人在你上面放的悬浮窗、连点器、辅助按钮，触摸全部被吃掉。

Aurora 现在（root 裸图层形态）的做法完全不同：

- 触摸区域**不是全屏**，而是**当前真正可见的 UI 形状的并集** ——
  窗口矩形、滚动条、每一个按钮/滑条的命中矩形逐个记录，合并成 `Region`
  交给 SurfaceFlinger；
- 玻璃没盖到的地方，触摸**直接穿透到下层**，别人的悬浮窗照常工作；
- 输入走 **WindowManager 的正规 `InputChannel`**，不抢 `/dev/input`、
  不做 `EVIOCGRAB`、不独占输入设备。

> 实测：与第三方连点器悬浮窗**同时运行互不干扰** ——
> 对方的按钮照样能点，我们的玻璃面板也照常响应。
> 这一条正是"全屏盾"方案做不到的。

### 痛点 2：ImGui 的输入框调不出系统输入法

ImGui 是纯原生绘制，`InputText` 只是一块自绘画布，**没有 Android 的 `InputConnection`**，
所以点上去不会弹键盘；就算硬弹了，键盘贴着屏幕底部，而我们的图层在整棵窗口树之上，
**键盘会被我们自己的触摸区域盖住，按键点不动**。

Aurora 的做法（`ime-bridge/`）：

- 一个独立的 Java 桥接服务与 native 通过自定义协议通信，负责拉起/收起系统输入法、
  回传"整段已提交文本 + 选区"；
- native 侧把整段文本换算成**增量**（公共前缀 + 按 UTF-8 字符退格 + 插入），
  而不是无脑追加 —— 否则敲 `a` 再敲 `b` 会变成 `aab`；
- **把键盘矩形从触摸拦截区里挖掉**，键盘按键才点得动；
- 键盘收起后复位焦点状态，避免"键盘再也叫不回来"。

### 痛点 3：多个 ImGui 窗口互相冲突

同一个进程里开多个窗口 + 弹窗，很容易出现：参数互相串、拖动一个动两个、
弹窗把父窗口排版搞乱。

Aurora 的做法：

- 每个组件实例持有**自己的参数副本**（按钮 1 改参数不会动按钮 2）；
- 弹窗绘制前后**存取排版光标**，弹窗不再污染父窗口的内容流；
- 每个窗口的触摸形状独立记录，拖动 / 滚动 / 长按缩放 / 组件点击有明确的
  **优先级仲裁**（组件 > 拖动条 > 滚动），且这些仲裁内核都是纯逻辑、有离线回归。

### 痛点 4：想调一个参数，得改代码重编

Aurora 内置参数工作台：**35 个目标 / 1134 条参数**，每条都**指针绑定到真实渲染字段**
（不是"看起来能调、其实没接线"的假控件），支持实时生效、撤销重做、预设、导入导出、
A/B 对比，以及原子写盘的自动保存。

### 痛点 5：悬浮窗的"实时背景"必定撕裂

见第三节 —— 这是本项目花力气最多、也最容易被忽略的一条。

## 二、液态玻璃：真光学，不是系统模糊

Android 自带的 `setBackgroundBlurRadius` 只有一层 Kawase 模糊 ——
没有折射、没有色散、没有边光，而且完全不可调。Aurora 的玻璃是自己写的着色器管线：

| 效果 | 实现 |
|---|---|
| 模糊 | 可分离两趟 gather，每向 12 抽头，σ = 模糊半径/√3，自动降采样 |
| 折射 | 圆角矩形 SDF 的外法线驱动位移，位移**恒朝面板内部** |
| 色散 | 7 抽头 / 3 对，按折射强度与光谱系数分配 |
| 边光 | 45° 方向光梯度 + 均匀描边两层可选 |
| 内阴影 / 发光 / 液滴融合 | 独立场，可分别开关 |
| 抗锯齿 | `fwidth` 覆盖率，不是硬边 |

关键性能取舍（都有离线断言守着）：

- **采样留白只为模糊留**：既然折射位移恒朝内，采样区只需覆盖模糊核触达距离
  （3σ+1px），不必为折射预留 —— 采样面积 **−23%**、模糊目标面积 **−45%**；
- **降采样网格锚定**：`pitch` 严格等于降采样倍数，避免"改留白导致亚像素相位漂移"
  （真机上量到过：最大 55 灰阶的边缘重影，修正后降到 ≤2 灰阶）。

## 三、实时背景：为什么它不撕裂

**问题本质**：覆盖层要显示"玻璃下面是什么"，只能去**采样已经合成好的屏幕**。
于是窗口内是"1 帧前的画面"，窗口外是"当前帧直出" ——
**两条时间线拼在一起**，运动物体跨过边界时就会错位，看起来就是撕裂。

> 实测验证：把玻璃的光学参数**全部调成 0**（纯透明板），现象依旧 ——
> 所以它跟光学、跟渲染性能都无关，**纯粹是架构问题**。

**Aurora 的解法（全屏接管）**：

不去消除延迟，而是**消除不一致** —— 把采样到的"世界底层"**不透明地铺满整屏**，
玻璃画在它上面。这样：

- 整块屏幕来自**同一条时间线**，接缝从结构上不存在；
- 延迟变成**全屏一致**的约 0.6~1.0 个源帧（120Hz 下 5~8ms）——
  人对"一致的 6ms"几乎无感，对"不一致的 6ms"极其敏感；
- 世界底层不可用时自动退回透明覆盖层，**不会黑屏、不会显示冻结画面**。

**必须说清楚的物理边界**：零延迟做不到。玻璃要采样的画面必须先被系统合成出来，
所以下限就是 1 帧。要真正零延迟，只有让玻璃和背景在**同一次合成**里产生
（即在 SurfaceFlinger 内部做）—— 但那样只能拿到系统自带的 Kawase 模糊，
没有折射/色散/边光，那已经不是液态玻璃了。

## 四、帧率与延迟：120fps 是怎么稳住的

一路上量到的数字（测试机 / 骁龙 8 Elite / Android 16，1080×2376）：

| 项目 | 优化前 | 优化后 |
|---|---|---|
| `eglSwapBuffers` 耗时 | 14.1ms（被 vsync 回压拖住） | **0.5ms** |
| 背景时间差 | 2.53 帧 | **0.6~1.0 帧** |
| 渲染帧率 | 60fps 锁死 | **118~120fps** |
| 采样面积 | 100% | 77% |

关键改动：

1. **交换间隔设 0**：安卓的 BufferQueue 变成"取最新可丢"，不再被驱动回压拖住整条流水线；
2. **帧率投票 + 绝对时间网格**：向 SurfaceFlinger 声明 120fps，用绝对时间网格保证
   长期帧率严格不超标，同时允许单帧提前开画（用上新到的背景帧）；
3. **场景自适应调度**（刻意"不写死"）：渲染线程优先级**按场景动态升降**，
   系统繁忙或检测到别的高刷前台时**主动让路** ——
   骁龙 8 Elite 只有 2 个 prime 核，游戏/相机/系统 UI 同样在抢，
   把渲染线程死绑在那两个核上对谁都没好处。

| 场景 | nice | uclamp | 绑核 |
|---|---|---|---|
| 系统忙 ≥70%（多半在打游戏） | 0 | 0% | 否 |
| 检测到其它高刷前台 | 0 | 0% | 否 |
| 玻璃未显示 | 0 | 0% | 否 |
| 玻璃静止 | −4 | 20% | 否 |
| 交互中 | −6 | 30% | 否 |
| 交互中 + 高刷 + 系统空闲 | −10 | 50% | 否 |

激进的绑核（把渲染线程钉在 prime 核上）是**显式选项**，不是默认行为。

## 五、架构

```
root-host/elf/          root 裸图层宿主（本项目的主角）
  aurora_overlay.cpp      入口：参数、后端菜单、显示选择、主循环、诊断
  aosp_glue.h             直连 SF / WMS 的私有 ABI（符号运行时校验，解不出就拒绝创建）
  HapticBinder.h          震动：Binder 直连 vibrator_manager
  DisplayPick.h           从 dumpsys 解析显示列表

app/src/main/cpp/       共享的渲染与 UI 运行时
  Renderer.*              渲染线程、帧节拍、场景自适应调度
  GlesBackend.*           EGL/GLES3 后端、投影纹理、全屏接管
  VulkanBackend.*         Vulkan 后端（承载 ImGui 那一层）
  GlesSceneCompositor.*   世界底层合成
  ThreadTuning.h          调度策略（纯逻辑，可离线回归）
  glass/                  参数模型 / 注册表 / 预设 / 撤销
  third_party/imgui/      固定的 Dear ImGui
  third_party/liquidglass/液态玻璃着色器管线（ytbl）

ime-bridge/             输入法 Java 桥接
tests/                  38 项离线回归（纯逻辑，PC 上跑，不需要设备）
docs/                   设计与踩坑记录
```

几乎所有容易出错的内核都抽成了**纯逻辑头文件**（手势仲裁、布局、调度策略、采样留白、
输入法文本换算、时间戳换算……），所以它们能在一台没有手机的 PC 上被逐值断言。

## 六、两种宿主形态

仓库里同时存在两种宿主，它们的**输入模型完全不同**，值得分清：

| | Activity 宿主（早期形态） | **root 裸图层宿主（当前主线）** |
|---|---|---|
| 怎么建窗口 | `TYPE_APPLICATION_OVERLAY` 窗口 | SurfaceFlinger 里 `mRoot` 的兄弟图层 |
| 触摸 | **全屏输入盾消费所有触摸** | **只拦截可见 UI 形状**，其余穿透 |
| 背景来源 | 用户授权的 MediaProjection 投屏帧 | SF 镜像（`setDisplayIdToMirror`） |
| 需要 | 普通权限 + 用户授权 | **root** |
| 与其它悬浮窗共存 | ❌ 会打架 | ✅ 互不干扰 |

早期形态的完整说明保留在 [`docs/README_activity_host_legacy.md`](docs/README_activity_host_legacy.md)。

## 七、快速开始

**要求**：root（KernelSU / Magisk 均可）、Android 12+、AArch64。
本项目直接调用 SurfaceFlinger / WindowManager 的私有 ABI，**不是**公开 API 的封装。

```sh
# 1. 构建（需要 NDK 27.0.12077973 + CMake 3.22.1）
cmake --build build/elf-arm64 --target aurora_overlay -j 8

# 2. 推送
adb push build/elf-arm64/bin/aurora_overlay /data/local/tmp/
adb shell su -c "chmod 755 /data/local/tmp/aurora_overlay"

# 3. 跑在物理主屏上（display 0；--yes-physical 只是安全确认，不会创建虚拟屏）
adb shell su -c "cd /data/local/tmp && ./aurora_overlay --display 0 --yes-physical --max-seconds 3600"
```

> **关于显示选择**：`--display 0 --yes-physical` 表示"画在物理主屏上"，
> 这两个参数都**不会**创建虚拟显示。若要让它在**虚拟屏**上跑（无头验证、不占用自己的屏幕），
> 改用 `--display-id <id>`，先自己查：
>
> ```sh
> adb shell dumpsys SurfaceFlinger --display-id     # 取 "Virtual display" 那行的 id
> ```
>
> ★ 这个 id **每次重建虚拟屏都会变**，所以工具本身从不硬编码它、也不按它匹配。

在**交互式终端**里启动会先出现一个渲染后端菜单（OpenGL ES / Vulkan，10 秒不选走默认）；
非交互启动（管道、后台）不会等待，直接使用默认值。也可以直接指定：

```sh
./aurora_overlay --backend vulkan ...      # 或 --backend gles
```

> **注意**：Vulkan 后端目前只承载 ImGui 那一层。
> 液态玻璃的光学与场景合成器都是 GLES 实现的，所以 Vulkan 下不绘制玻璃 ——
> 它的用途是在同一台设备上量出"玻璃这一层值多少开销"。

### 诊断开关（默认全关，零开销）

| 变量 | 作用 |
|---|---|
| `AURORA_FULLSCREEN_TAKEOVER=0` | 关掉全屏接管，回到透明覆盖层 |
| `AURORA_SCHED_TUNING=0` | 关掉调度优化 |
| `AURORA_SCHED_PIN=1` | 把渲染线程钉到 prime 核（激进） |
| `AURORA_CAPTURE_PAD_LENS=1` | 采样留白回到旧行为（A/B 用） |
| `AURORA_SWAP_INTERVAL=1` | 交换间隔回到 vsync 锁定（A/B 用） |
| `AURORA_FRAME_RATE_VOTE=0` | 关闭向 SF 的帧率投票 |
| `AURORA_NO_GATHER=1` | 跳过模糊（分层诊断） |
| `AURORA_NO_BACKDROP=1` / `AURORA_NO_SHADOW=1` | 逐层隔离光学效果 |
| `AURORA_FRAME_DIAGNOSTICS=1` | 输出每帧性能明细 |

### 离线回归

```sh
pwsh -File tests/run_host_tests.ps1      # 38 项，全部纯逻辑，不需要设备
```

## 八、已知限制

诚实列出来，免得你踩坑：

- **需要 root**，且直接依赖厂商 ABI（不同 OEM 可能需要适配符号偏移）；
- **零延迟不可能**（原因见第三节），本项目做到的是"全屏一致的低延迟"；
- **受保护内容抓不到**：安全界面（密码、支付）与 DRM 视频在镜像里是黑的，
  这类场景必须依赖 fail-safe 退回，不能只靠全屏接管；
- **Vulkan 后端不含玻璃光学**；
- 目前主要在**测试机 / 骁龙 8 Elite / Android 16** 上验证，
  其它机型需要重新核对显示与输入相关的结构体偏移；
- 本项目涉及系统级注入，**请只在自己的设备上使用**。
  因使用本软件导致的设备异常、数据丢失、账号风险，作者不承担责任。
